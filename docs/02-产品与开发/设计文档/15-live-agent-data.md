# Agent 真实数据获取、恢复与展示验收

2026-10-13，Codex。用户授权持续修复 MCP、爬虫与前端链路。复用现有 LangGraph、ToolBroker、SQLite checkpoint 和原文核验；生产历史未导入验收客户，真实 Key 仍只读 `config/apikey.txt`。

## 为什么原结果是 0

生产任务 `4a89378682cb4c2ba6730d4dd0f47211` 的账本显示企查查 basic 已成功保存 4 个工商字段，BidResearch 也取得两篇必联网正文。不是所有工具都没有调用。具体断点如下：

1. 正文“第二成交候选人为：成都宏天智电子有限公司”及“备选成交”供应商表未被正确解析，真实候选没有进入 TenderRecord。
2. 同企业两次采购检索的时间窗分别为 365 与 30 天，失去账本复用，重复消耗详情预算。检索标题通常没有企业名；超时未取得详情时，列表入口又被过早删除。
3. 原生解析已有合格软件采购买方时，另一页面的模型连接失败会中断整批保存。降级后的失败标记也没有按来源清除，恢复成功仍可能显示 partial。
4. 外部工具超过 stdio 超时时，已完成的列表与正文会一起丢失。应用读取招投标详情与外部 MCP 详情的解析入口不统一。
5. 企业来源统计和文档入口遗漏招投标 Evidence；候选独有企业在无模型超时摘要里也被漏掉，造成“全是 0”的印象。

采购人、候选、最终中标、客户、供应商是不同角色。取得候选公告，不能把“采购方”自动变成本企业客户；未取得企业自身采购公告，不能解释为没有采购需求。

## 修复后的执行规则

- 应用与固定外部工具同步支持成交候选人及备选表格，逐条按原文供应商列、连续引文核验；未知金额、掩码号、日期保持未知。
- 同企业 procurement 检索继承原 `tender_days`，默认 365 天，复用同 Job 的实际调用；保留后续补读额度。
- 经平台列表证据、域名和当前公司查询核验的结果只作为导航入口，不能作为事实。后续实际 HTTP 读取详情，才进入核验。
- 已成功解析的公开采购公告继续经过原主体、软件服务相关性、角色、截止及持久化门禁。模型失败不丢这些候选，未分析页面持久化具体来源 ID。
- 显式恢复先分析失败的归档正文；包括已达客户数量上限的情况。分析同一来源成功才清其标记；其他页面成功不能清未完成来源。工具/模型/时间预算不重置。
- 外部工具有内部总时限；每个已完成步骤原子写 `partial.json`。stdio 超时仅可读取本次 UUID 输出快照，再走同一归档/匹配/原文门禁；记录 `partial_recovery=true`，不能冒称完整返回。
- QCC 网络超时与连接失败分类为 timeout/unavailable，不把协议连接失败误说成 Key 无效。前端展示安全中文原因。
- 企业来源统计包含本企业 TenderRecord/TenderRelation 的实际 Evidence，文档入口保留角色/统计口径与连续原文；其他企业或同任务无关来源仍拒绝。
- 无模型摘要也报告具体候选项目和链接，明确候选非成交及“未核验到采购需求不代表没有需求”。正常 AI 分析仍引用完整结构化记录，未知具体规格不补造。
